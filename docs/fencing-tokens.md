# Fencing tokens and split-brain mitigation

A distributed lock service alone cannot guarantee safety in asynchronous networks. Even if the lock service maintains consensus, client workers can experience unpredictable execution delays, such as garbage collection pauses, operating system paging, or transient network partitions.

## The split-brain problem in distributed locks

Consider a system where Worker A acquires a 10-second lease on partition `partition-0` to write records to a database:

1. Worker A acquires the lease.
2. Worker A enters a stop-the-world garbage collection pause that lasts 15 seconds.
3. While Worker A is paused, its 10-second lease expires on the coordination cluster.
4. Worker B requests the lock for `partition-0`. The cluster grants it because the previous lease expired.
5. Worker B writes changes to the database.
6. Worker A resumes execution from its garbage collection pause. Worker A is unaware of the elapsed time and executes its pending database write.
7. Worker A overwrites Worker B's data, causing silent corruption.

Clock synchronization algorithms like NTP cannot prevent this because the worker cannot predict when a pause will occur relative to its local time checks.

## How fencing tokens solve the problem

A fencing token is a monotonic 64-bit integer generated by the consensus engine. Every time a lock is acquired or reassigned, the cluster increments the global token counter:

1. Worker A acquires the lease on `partition-0`. The cluster issues Fencing Token `101`.
2. Worker A pauses for 15 seconds.
3. The cluster detects the expired lease. Worker B requests the lock.
4. The cluster issues Fencing Token `102` to Worker B.
5. Worker B writes to the database, supplying token `102`. The database updates its recorded highest token for `partition-0` to `102` and accepts the write.
6. Worker A wakes up and sends its write to the database, supplying token `101`.
7. The database checks the incoming token against the stored token: `101 < 102`.
8. The database rejects Worker A's write.

## Storage guard implementation

Downstream storage systems enforce fencing by checking that each write includes a token strictly greater than the highest token observed for that partition.

Example in PostgreSQL:
```sql
UPDATE partitions
SET data = '...', last_fencing_token = 102
WHERE partition_id = 'partition-0' AND last_fencing_token < 102;
```

If the row count is zero, the application knows a newer worker has taken over and halts execution.
